# i32 vs u32 for pair counts

Related docs: [RESEARCH.md](RESEARCH.md#i32-vs-u32) (short summary), [DEVELOPMENT_NOTES.md](DEVELOPMENT_NOTES.md) (trainer write-up), [CLAUDE.md](../CLAUDE.md) (conventions).

Pair counts in `compute_pair_freqs` are `u32`:

```rust
fn compute_pair_freqs(
    splits: &HashMap<&str, Vec<String>>,
    word_freqs: &HashMap<&str, u32>,
) -> HashMap<(String, String), u32> {
    let mut pair_freqs: HashMap<(String, String), u32> = HashMap::new();

    for (word, freq) in word_freqs {
        let split = splits[word].clone();
        for window in split.windows(2) {
            let pair = (window[0].clone(), window[1].clone());
            *pair_freqs.entry(pair).or_insert(0) += freq;
        }
    }
    pair_freqs
}
```

Training-phase function: it counts each adjacent symbol pair in the corpus so the trainer can pick the next merge. Encoding counts nothing, it replays the merges training produced.

## Why u32

Counts are never negative, and `u32` has twice `i32`'s range (about 4.29 billion vs 2.15 billion). That raises the limit, it does not remove it. A pair occurs at most once per byte position, so a count cannot exceed the corpus size in bytes: `u32` is safe up to about 4.29 GB, larger corpora need `u64`.

The earlier version used `i32`. The change touched the map in `tokenize_bpe` and three types in `compute_pair_freqs`:

```text
 // tokenize_bpe
-let mut word_freqs: HashMap<&str, i32> = HashMap::new();
+let mut word_freqs: HashMap<&str, u32> = HashMap::new();

 // compute_pair_freqs
-    word_freqs: &HashMap<&str, i32>,
-) -> HashMap<(String, String), i32> {
-    let mut pair_freqs: HashMap<(String, String), i32> = HashMap::new();
+    word_freqs: &HashMap<&str, u32>,
+) -> HashMap<(String, String), u32> {
+    let mut pair_freqs: HashMap<(String, String), u32> = HashMap::new();
```

## What happens on overflow

A debug build panics with `attempt to add with overflow`. A release build wraps silently unless `overflow-checks` is on, and the trainer then picks a wrong merge from the wrapped count. `u64`, `checked_add` or `saturating_add` avoid this.

```rust
// current: panics in a debug build, wraps in a release build
*pair_freqs.entry(pair).or_insert(0) += freq;

// explicit: panics in every build, with a clear message
let slot = pair_freqs.entry(pair).or_insert(0);
*slot = slot.checked_add(*freq).expect("pair count overflowed u32");
```

For a pair at `u32::MAX` with `freq = 2`, the first version panics with `attempt to add with overflow` in a debug build and leaves the count at 1 in a release build. The second panics with `pair count overflowed u32` in every build.

## Counting cost

`+= freq` adds the chunk's frequency, not 1, because `word_freqs` stores each distinct chunk once with its count. Every pair is still recounted after each merge; a faster trainer updates counts only for chunks a merge changed. See [Cost](DEVELOPMENT_NOTES.md#cost).
