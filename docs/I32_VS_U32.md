# i32 vs u32 for pair counts

Related docs: [RESEARCH.md](RESEARCH.md#i32-vs-u32) (short summary), [DEVELOPMENT_NOTES.md](DEVELOPMENT_NOTES.md) (trainer write-up), [CLAUDE.md](../CLAUDE.md) (conventions).

The pair counts in `compute_pair_freqs` are `u32`:

```rust
fn compute_pair_freqs(
    splits: &HashMap<&str, Vec<String>>,
    word_freqs: &HashMap<&str, u32>,
) -> HashMap<(String, String), u32> {
    let mut pair_freqs: HashMap<(String, String), u32> = HashMap::new();

    for (word, freq) in word_freqs {
        let split = splits[word].clone();
        for window in split.windows(2) {
            let pair = (window[0].clone(), window[1].clone());
            *pair_freqs.entry(pair).or_insert(0) += freq;
        }
    }
    pair_freqs
}
```

This function is part of the training phase. It counts how often each adjacent pair of symbols occurs in the corpus so the trainer can choose the next merge. Encoding does not count pairs. It applies the merges that training already produced.

## Why u32

A count is never negative, and `u32` has twice the range of `i32` (about 4.29 billion instead of 2.15 billion). This only raises the limit. A pair can occur at most once per byte position in the corpus, so a count cannot exceed the corpus size in bytes. That makes `u32` safe for corpora up to about 4.29 GB. Larger corpora would need `u64`.

The earlier version used `i32`. The change touched the map in `tokenize_bpe` and the three types in `compute_pair_freqs`:

```text
 // tokenize_bpe
-let mut word_freqs: HashMap<&str, i32> = HashMap::new();
+let mut word_freqs: HashMap<&str, u32> = HashMap::new();

 // compute_pair_freqs
-    word_freqs: &HashMap<&str, i32>,
-) -> HashMap<(String, String), i32> {
-    let mut pair_freqs: HashMap<(String, String), i32> = HashMap::new();
+    word_freqs: &HashMap<&str, u32>,
+) -> HashMap<(String, String), u32> {
+    let mut pair_freqs: HashMap<(String, String), u32> = HashMap::new();
```

## What happens on overflow

If a count does overflow, a debug build panics with `attempt to add with overflow`. A release build wraps around without any error unless `overflow-checks` is enabled, and the trainer would then choose a wrong merge from the wrapped count. Using `u64`, or `checked_add` or `saturating_add`, avoids this.

```rust
// current: panics in a debug build, wraps in a release build
*pair_freqs.entry(pair).or_insert(0) += freq;

// explicit: panics in every build, with a clear message
let slot = pair_freqs.entry(pair).or_insert(0);
*slot = slot.checked_add(*freq).expect("pair count overflowed u32");
```

For a pair already at `u32::MAX` with `freq = 2`, the first version panics with `attempt to add with overflow` in a debug build and leaves the count at 1 in a release build. The second panics with `pair count overflowed u32` in every build.

## Counting cost

`+= freq` adds the chunk's frequency rather than 1, because `word_freqs` stores each distinct chunk once with its count. The function still recounts every pair after each merge. A faster trainer would update the counts only for the chunks that a merge changed. See [Cost](DEVELOPMENT_NOTES.md#cost).
